# 产品经理 SOP

版本：1.1\
更新日期：2026-11-01\
适用范围：你配合 AI 推进一个产品需求，并与设计、研发、测试、运营、数据等角色协作。\
配套文件：[需求推进模板](../assets/requirement-template.md)

## 1. 怎么使用这套 SOP

收到想法、用户反馈、业务要求或指标问题时，先查当前项目是否已有同一需求的推进记录，有就继续更新原文件。只有新需求才复制一份需求推进模板，按“项目名-需求名-推进记录.md”命名，放在对应项目的文档目录。

第一次只需要填清：需求名称、产品与端、问题来源、希望解决的问题、已有资料、当前进度。其余内容随工作补齐。未知项写“待确认”，并说明谁来补、什么时候或满足什么条件再检查；不适用项写明原因。

从实际进度进入流程。已有分析、原型或已确认规则时，先检查能否复用，再补缺口。每次结束当前工作，更新模板顶部的交接摘要：当前结论、依据、已确认范围、产出位置、未决问题、下一步及责任人。

### 选择流程强度

| 模式 | 适用条件 | 怎么执行 |
| --- | --- | --- |
| 快速流程 | 已知规则下的文案、展示或小范围体验调整，影响明确 | 完成需求收口、范围确认、相应修改、验收、发布核查及简短结果记录；分析、原型和正式评审可合并或跳过，记录理由 |
| 标准流程 | 新功能、跨页面流程、业务规则或重要转化环节调整 | 按下面八步推进，复用已有材料，分析与验证深度随影响调整 |
| 探索流程 | 用户需求、商业模式、付费机制或技术可行性尚不清楚 | 先做问题分析和关键假设验证，再决定是否进入交付；可以得出暂缓或不做的结论 |

改动大小不只看页面数量。一个按钮如果影响扣费、权益或核心数据，也需要相应的规则、验证和专业角色参与。只要求分析或原型的任务，可以在该项交付后结束；后续开发、发布按实际任务范围推进。

新建快速任务的记录时，只展开当前完成点用到的章节，其他阶段在进度表中说明未开展或不适用即可，不必保留整套空表。接续已有记录时保留用户已写内容，后续需要哪个环节再补充。

### 分工

| 角色 | 负责什么 |
| --- | --- |
| 你／产品负责人 | 明确目标，判断用户与业务价值，决定优先级和范围，处理业务取舍，确认产品验收与后续方向 |
| AI 与 Skill | 整理已有事实，产出授权范围内的分析、草稿和原型，检查遗漏与矛盾，维护记录；不虚构用户反馈、团队结论或验证结果 |
| 设计 | 提前参与目标路径和体验设计，判断可用性与视觉方案 |
| 研发 | 提前判断技术可行性、依赖、工作量和排期，负责实现与技术验证，按职责执行发布 |
| 测试 | 提前参与验收场景，验证实际版本、异常分支和回归范围 |
| 运营／数据等相关方 | 按需确认业务规则、运营准备、指标口径、数据可用性和观察结果 |

一个人可以兼任多个角色，记录实际参与者即可。日常整理、检查和既定范围内的执行直接推进；涉及目标、范围或关键业务取舍的变化，说明原因和影响，由相应负责人作决定。已有授权继续有效，不逐次重复确认。

## 2. 两个 Skill 的调用规则

### 什么时候调用

| 场景 | 调用选择 | 输入 | 产出及下一步用途 |
| --- | --- | --- | --- |
| 看不清现有付费、权益、充值、解锁或不付费分支 | 第 2 步调用 `pm-payment-journey` | 产品链接、截图、规则或已有报告；产品与端、账号状态、观察范围 | 完整路径分析 HTML；据此提取事实、摩擦、假设和验证指标，进入优先级与方案判断 |
| 新方案调整付费门槛或权益关系，需要比较路径 | 第 4 步按需再次调用 `pm-payment-journey` | 当前报告、拟议变化、已确认规则 | 更新原报告，明确区分当前事实和拟议方案；为目标路径设计提供依据 |
| 已有明确范围，需要表达页面、交互和状态 | 第 4 步调用 `pm-prototype-workbench` | 需求、产品／端／页面清单、规则来源、参考材料、已有工作 HTML | 可编辑三栏工作 HTML；用于体验、验证和完善说明 |
| 需要把已确认文字、数据需求或页面说明写进原型 | 第 5 步调用 `pm-prototype-workbench` | 原工作 HTML、明确提供的文字、适用产品与页面 | 更新同一工作文件；供研发理解和测试设计使用 |
| 评审后或开发中已决定修改方案 | 第 6 步按需调用 `pm-prototype-workbench` | 当前工作文件、确认后的变更、影响范围 | 更新原型及相关说明，保持交付依据一致 |
| 验收实际实现 | 第 7 步对照原型和已确认规则 | 当前评审依据、实际构建／环境、验收场景 | 验收记录；只有方案本身发生确认后的变化才更新原型 |
| 上线数据指向某个付费门槛，或产品路径发生变化 | 第 8 步按需调用 `pm-payment-journey` | 当前产品、原报告、观察条件、实际数据 | 更新路径与观察边界，形成下一轮问题；后续要改方案时再调用原型 Skill |

纯文案改动、已有结论的整理，不必调用这两个 Skill。通用注册、新手引导等问题按实际需要研究，不能默认付费路径 Skill 已完整覆盖。后台指标归因需要行为或交易数据，路径报告只能提供机制解释和待验证假设。

### 两种交付物分别怎么验收

**路径分析 HTML**：默认保留产品模式、套餐与定价、用户行为路径、内容发现、付费与不付费路径、付费点影响分析、关键摩擦、验证指标、证据与观察边界九个板块。总图在前，场景详图在后，每个门槛分别呈现适用分支。资料不足的部分注明边界。

检查节点与连线高亮、下一步选择、上一步、只看当前路径、恢复全图／Esc、说明展开和放大阅读；实际走查过的产品路径、报告自身的交互、真实支付或解锁结果分别记录。存在签到证据才加入签到获权与使用分析。

**原型工作 HTML**：默认交付可编辑工作文件，保留三栏、产品与页面目录、需求文字入口和页面标注。依据用户提供的需求实现交互；未提供的业务规则和研发说明不主动补写。明确要求设计规则时，可在指定范围内起草，业务建议与已确认规则保持可辨认。

检查主要交互、状态切换、目录、说明定位、编辑暂存、适用屏幕尺寸和已有内容保留情况。实际运行界面检查是完成条件，脚本通过不能代替视觉检查。修改已有文件先保留备份，再更新正在使用的文件。

工作台里的文字入口只支持纯文字；Markdown 表格需要转成清楚的文字说明，或在推进记录中维护并引用。浏览器暂存不等于写入文件；重要修改后由用户手动保存可编辑副本，或按用户明确要求保存。交接时记录实际文件位置和修订日期。

只读 HTML 与 PRD 导出由用户手动触发，或按用户明确要求执行；普通“做原型”“完善需求”不触发额外导出。路径报告继续使用其分析报告格式。

## 3. 八步操作流程

### 第 1 步：收口需求与目标

**何时开始／输入**：收到一个新想法、反馈、业务要求或指标问题；输入原始描述、相关资料及已知约束。

**怎么做**：

1. 保留原始诉求和来源。把“要加一个功能”进一步拆成目标用户、发生场景、当前困难、希望出现的变化。
2. 说清产品、端、涉及入口和用户状态；现有页面或规则能查到的先查，不凭页面名称猜测。
3. 写一句目标，并提出成功判断方式。指标基线和目标值有依据就填，没有就标缺口，不编造提升比例。
4. 列明已知范围、暂不涉及的部分、时间与资源约束。区分业务期望日期和实施方已经确认的日期。
5. 将关键缺项放入模板的统一待办表，区分信息缺口与需要负责人决定的取舍。能够独立推进的部分继续进行。

**Skill**：本步通常无需调用两个专项 Skill；如果资料已经足够且任务直接是分析或原型，可接入对应步骤。

**产出**：模板“1. 需求简报”和顶部工作摘要。\
**参与者**：你／产品负责人；必要时核对需求提出者的原始意图。

**完成标准**：能够说明为谁解决什么问题、依据从哪里来、预期改变什么；已知范围与关键未知清楚。接着进入第 2 步，或复用已有证据进入第 3 步。

**缺项怎么处理**：目标或产品范围存在冲突时先收敛；一般资料缺失记入待办，继续不依赖它的工作。

### 第 2 步：研究现状与用户路径

**何时开始／输入**：问题已收口，需要确认现状、原因或影响；输入需求简报、产品入口、现有报告、用户反馈或数据。

**怎么做**：

1. 先列本次必须回答的问题，例如“余额不足后用户有哪些选择”“权益是否覆盖目标内容”。围绕问题选材料，不固定做一套完整竞品调研。
2. 记录观察日期、端、账号／会员状态及访问范围。读取原报告和当前页面，必要时补充用户反馈、访谈或行为数据。
3. 梳理入口、目标、前置条件、动作、门槛、分支与结果；区分暂缓购买、换内容、结束本次访问等不同去向。
4. 对每项结论标明性质：实际观察、页面声明、数据结果、机制推断或待验证。记录来源及适用条件。
5. 付费与权益问题调用路径分析 Skill，检查完整 HTML 和路径交互；通用体验问题按相应路径分析，不强套付费结构。
6. 提取最重要的事实、摩擦和假设。对尚未确定的原因写验证方法和所需证据，不把“可能影响转化”写成已造成转化变化。

**Skill**：满足付费／权益路径场景时调用 `pm-payment-journey`；已有同产品报告就更新原文件。\
**产出**：路径分析 HTML（适用时）、模板“2. 证据与当前路径”、待验证事项。\
**参与者**：产品负责分析；数据、运营或用户提供与问题直接相关的证据。

**完成标准**：主要路径与观察边界清楚，关键判断能追溯来源，证据不足之处有后续办法。将摘要交给第 3 步。

**缺项怎么处理**：页面受限时记录未覆盖路径，利用可得材料继续；要下行为、到账或收入结论时补相应证据。分析本身不授权购买、领取或消耗权益。

### 第 3 步：判断价值、优先级和范围

**何时开始／输入**：已有问题与初步证据，需要决定投入方向；输入证据摘要、目标、约束及候选方向。

**怎么做**：

1. 说明问题影响哪些用户、发生频率和后果；数据未知就写定性判断及不确定性。
2. 比较可行方向，包括调整现有流程、减少摩擦、补充信息或新增能力；也保留暂缓和不做的选择。
3. 从用户收益、业务收益、成本、依赖和证据强弱说明优先级。简单任务用文字判断即可，需要比较多个需求时再选择评分方法。
4. 与研发核对关键技术依赖、可行性和工作量，与相关方核对业务约束。未确认的估计保留估计性质。
5. 决定做、先验证、暂缓或不做，并记录原因、决定人和日期。需要验证时写清验证通过后如何决定。
6. 对要做的需求划定最小范围和本次不做的部分，确定目标路径、影响产品／端以及暂定成功标准。

**Skill**：使用第 2 步的结果，不需要为本步重新调用两个 Skill。\
**产出**：模板“3. 决策与范围”，必要的验证任务或依赖。\
**参与者**：你／产品负责人作业务取舍；研发及相关方提供专业判断。

**完成标准**：决定、范围、理由和下一步明确；进入方案设计的范围已确定。关键可行性未知时，先安排相应验证。

**缺项怎么处理**：证据不足则返回第 2 步或做小范围验证；暂缓需求写清重新评估的条件；不做的需求保留理由后结束当前推进。

### 第 4 步：设计方案与交互验证

**何时开始／输入**：需要验证方案或表达已确定范围；输入范围、当前路径、已有规则、页面参考和工作 HTML（如有）。

**怎么做**：

1. 先写目标任务路径：什么状态下进入、用户做什么、系统怎样响应、结果是什么、如何返回或继续。
2. 列产品、端、页面及关键状态。根据真实需求处理正常、无内容、失败、权限不足等适用情况，不为凑清单发明规则。
3. 对影响较大的方案差异说明取舍。优先验证最不确定的部分，必要时请研发做技术验证，请目标用户完成原型任务。
4. 明确本次原型任务是按已给规则实现、保留已有 HTML 进行转换，还是在指定范围内协助设计规则。已有授权直接沿用。
5. 调用原型 Skill。已有工作文件就在原文件上迭代，保留原内容与交互；无说明材料时允许说明为空，缺项放在推进记录中。
6. 在真实运行界面走通目标任务，检查关键分支、表单和弹窗状态、目录切换、说明定位及适用尺寸，记录文件版本、检查范围和发现的问题。
7. 记录验证对象、任务、表现与反馈。没有真实用户参与时，如实记录为内部走查；业务价值或可用性判断仍保留相应证据边界。

**Skill**：本步主要调用 `pm-prototype-workbench`；涉及付费关系的方案比较时，按需更新 `pm-payment-journey` 报告，并区分现状与方案。\
**产出**：可编辑工作 HTML、模板“4. 方案与原型验证”、问题和处理结论。\
**参与者**：产品与设计一起完善方案；研发参与可行性；必要时邀请目标用户验证。

**完成标准**：本次范围的关键交互可体验，主要不确定点已验证或有明确处理；原型与已确认规则一致。进入第 5 步补齐交付内容。

**缺项怎么处理**：交互实现问题直接修正后重查；若要改变已确认目标或范围，先说明证据、影响和取舍，取得相应决定后回到第 3 步调整。

### 第 5 步：整理规则、指标和验收要求

**何时开始／输入**：方案开始稳定，需要让研发、测试和数据角色据此工作；输入原型、已确认规则、验证反馈和目标。

**怎么做**：

1. 逐页面检查规则：适用人群、入口与前置条件、展示内容、操作结果、状态变化、适用的校验和异常处理。缺失内容按影响列待确认。
2. 把已提供或已确认的说明放到正确位置。需要 AI 设计某项规则时明确范围，建议与确认结果分别记录。
3. 按下表维护正文，工作台与推进记录各保留相应内容；同一业务规则指定一个维护位置，其他位置引用它。
4. 细化指标：定义、统计人群、分子分母或统计方式、来源、基线、目标依据、观察窗口及保护性指标。
5. 判断现有数据是否够用。有新增埋点需要时写事件、触发时机、必要字段及类型、身份关联和去重要求、验证方式；无新增需要时写清使用的现有数据来源。
6. 形成验收场景：前置状态 → 操作 → 预期结果。按实际影响覆盖关键正常分支、异常、权限／权益、数据上报和回归场景。
7. 请研发、测试和数据相关方检查是否可实现、可验证、可取数，将阻塞项列入统一待办。

| 内容 | 维护位置 |
| --- | --- |
| 背景、目标、范围和需求共用描述 | 原型“全局描述”；如果尚无原型，先在推进记录维护，迁入后保留引用 |
| 上线后看哪些数据、统计范围与观察时间 | 原型“上线后数据需求”；指标定义表可在推进记录维护并注明引用位置 |
| 已确认的事件、字段和触发条件 | 原型“埋点说明”，或已有埋点文档；指定一个维护位置 |
| 同产品跨页面、跨端的共用规则 | 原型“本产品全局说明” |
| 某个控件、页面或状态的规则 | 原型右侧页面研发说明，绑定对应位置 |
| 责任、决定、排期、待办、验收记录和复盘结果 | 需求推进记录 |

**Skill**：明确需要将文字写入或修改原型时调用 `pm-prototype-workbench`；单纯整理文档不用重新生成原型。\
**产出**：更新后的 PRD／原型说明、模板“5. 规则、数据与验收”，以及开发前必须解决的待办。\
**参与者**：产品负责需求表达；研发、测试、数据相关方检查各自依赖。

**完成标准**：规则有来源或确认依据，关键交互与文字一致，验收结果可以判断，效果数据有获取办法。阻塞开发的规则在进入实施前解决，或经决定移出范围。

**缺项怎么处理**：某项数据无法获取时，补采集方案或调整观察办法；指标变化影响目标判断时回到第 3 步确认。原型说明为空可以作为原型阶段交付，但不能被视作业务规则已经明确。

### 第 6 步：评审与开发跟进

**何时开始／输入**：需要确定交付依据和实施安排；输入当前原型／PRD、验收与数据说明、范围、依赖和未决项。

**怎么做**：

1. 评审前检查文件可访问，记录当前修订日期或快照位置。先给参会者一段交接摘要，让大家对齐本次目标和待决定事项。
2. 与实际参与的产品、设计、研发、测试评审；需要时邀请运营、数据等角色。重要问题可提前讨论，不必等所有文档完成。
3. 依次检查用户与业务价值、路径与体验、规则与异常、技术与依赖、指标与验收。AI 模拟评审可提前查漏，实际团队结论另行记录。
4. 记录通过、附条件通过或未通过。附条件通过要写清条件和期限；影响实施正确性的阻塞项未解决时，不把对应工作当作可直接实施。
5. 由实施方确认任务、工作量、依赖和排期；产品明确验收接口与需要参与的阶段。未经确认的日期保持待定。
6. 开发中有疑问，先查既有规则和决定。变化涉及范围或关键规则时，记录原方案、拟改内容、原因、影响和决定，再同步原型、数据与验收依据。
7. 按项目节奏检查交付进度和阻塞，更新当前依据。版本变化只回归受影响部分及其关联路径，不机械重复所有工作。

**Skill**：确认方案需要修改时调用 `pm-prototype-workbench` 更新原文件；仅进度同步或技术实现问题不触发原型重做。\
**产出**：模板“6. 评审、开发与变更”，当前交付依据和待办。\
**参与者**：产品组织对齐；研发、设计、测试等确认各自事项，发布安排由相应负责人落实。

**完成标准**：当前范围、依据、责任和实施安排一致；交付到测试时有明确构建／环境与已实现范围，可以进入第 7 步。

**缺项怎么处理**：意见冲突记录选项和影响，交给对应决策人；重大变化回到第 3～5 步补判断。未经实际确认的评审或排期不能填成“已确认”。

### 第 7 步：验收与上线

**何时开始／输入**：有可验证的实际版本；输入构建／环境、确认后的交付依据、验收场景及已知问题。

**怎么做**：

1. 核对测试环境、版本、构建、测试账号状态和配置，确认验证对象。凭据使用对应环境的受控来源，推进记录只保留环境与账号状态等必要信息。
2. 按第 5 步的场景操作真实运行界面，填写实际结果与证据；同时检查视觉、交互、适用屏幕尺寸和受影响旧功能。
3. 按实际需求核验提交后的状态、权限／权益变化、事件上报及可取数情况。点击成功与后台结果分别验证；真实购买、领取消耗等动作遵守已有授权范围。
4. 记录缺陷与影响。阻塞问题修复后回归；非阻塞遗留项由相应负责人作接受或延期决定，保留依据。
5. 给出产品验收与测试结论，列明覆盖范围和未验证项。确认适用的运营准备、配置、数据观察、发布与回退负责人和办法。
6. 按项目已有发布权限执行实际发布，记录环境、版本、时间、范围及操作人；超出当前授权的操作先落实所需决定。
7. 发布后检查实际环境与关键路径，确认相应数据可见，再进入观察期。记录失败、回退或残留问题，安排下一次核查。

**Skill**：使用原型作为对照。本步一般不调用两个 Skill；若验收暴露方案问题，先作方案决定，再更新原型和验收依据。

**产出**：第 5 步验收表的实际结果、模板“7. 发布与上线核查”、当前遗留事项。\
**参与者**：产品与测试确认各自验收结论；研发／发布负责人执行技术操作；运营、数据按需完成准备和核查。

**完成标准**：关键场景有当前版本证据，阻塞项已处理，发布记录及发布后核查可追溯。只有实际发布成功并有对应证据，才记为已发布；效果结论留到第 8 步。

**异常怎么处理**：验收失败返回实现或方案环节；发布异常按已有回退方案和权限处理。无法确认发布、验证或临时进程清理完成时，明确记录未完成，不标完成。

如提供、打开或重新打开 CMS 给你使用，先核对目标环境，从对应受控凭据来源读取并验证登录；同一条给你的回复中提供完整登录地址、当前有效账号和密码。取不到时明确缺项，不猜测或重置。实际密码不写入推进记录、仓库、长期记忆或跨对话通知。临时预览服务和测试进程在检查结束后精确清理。

### 第 8 步：效果复盘与下一轮决策

**何时开始／输入**：到达事先约定的观察时间或数据条件；输入发布记录、指标口径、实际数据、用户反馈及期间的重要变化。

**怎么做**：

1. 先核对数据覆盖、时间窗口、样本、人群、去重口径和上报延迟；确认本次版本与观察人群对应。
2. 对照基线和目标看核心指标，同时检查保护性指标；需要时按入口、渠道、用户状态、会员／权益状态等适用维度拆分。
3. 将现象与解释分开：发生了什么、有哪些可能原因、哪些已被证据支持、哪些仍待验证。
4. 核对同期活动、流量结构、其他版本和统计变化。没有合适的对照或实验时，说明前后变化的局限，不直接认定需求造成改善。
5. 回看目标路径。若问题指向付费门槛或权益使用，更新路径报告，将新观察与原有观察条件区分。
6. 决定继续、调整、停止或继续观察；写清行动、负责人、日期或复查条件。新范围进入下一轮需求记录，属于同一需求的补充验证则继续原记录。
7. 沉淀可复用的业务结论、规则或流程改进，并注明适用范围和证据；待办未闭环时保留状态。

**Skill**：需要重新核对付费／权益机制时调用 `pm-payment-journey`；确定要修改方案后，再进入第 3～4 步调用原型 Skill。\
**产出**：模板“8. 效果复盘”，更新的分析产物（适用时）和下一步行动。\
**参与者**：产品与数据相关方解释结果，相关业务负责人作后续投入决定。

**完成标准**：结果、证据、局限和行动明确。证据不足可以形成阶段性复盘，但效果状态保留“证据不足／继续观察”，并有下一次检查条件。

**缺项怎么处理**：数据缺失先修正采集或查询；假设不成立回到第 2～3 步调整。只完成发布不能替代效果复盘。

## 4. 可复制的 Skill 调用指令

替换【】中的内容后使用；已有上下文能够回答的字段直接沿用。指令里的产品事实来自当前需求，不套用其他项目。

### A. 分析付费与权益路径

```text
使用 $pm-payment-journey，分析【产品名】的【具体问题】。
产品与端：【填写】；账号／会员／权益状态：【填写或未确认】。
材料：【产品链接、截图、规则或原报告的绝对路径】。
重点回答：【列出本次需要回答的问题】。
已有报告：【路径；没有则写无】，请优先更新原报告。
区分当前观察、页面声明、机制推断和待验证项，保留观察日期与访问条件。
交付完整离线 HTML，检查路径选择、分支切换和恢复等交互；
把关键发现、产出位置和观察局限更新到【需求推进记录】。
```

### B. 按已有需求制作或迭代原型

```text
使用 $pm-prototype-workbench，为【需求名】制作／修改交互原型。
已确认需求和规则：【文件路径或明确文字】。
产品、端、页面及目标路径：【填写】。
当前工作 HTML：【绝对路径；新建则写无】。
本次范围：【要实现或修改的部分】。
按已给规则实现；未提供的业务说明留空，缺项记入【需求推进记录】。
已有文件保留原内容、交互和说明，在原工作文件上迭代。
交付可编辑工作 HTML，并记录实际界面与交互检查的范围和结果。
```

### C. 明确要求协助设计规则或补写说明

```text
使用 $pm-prototype-workbench，基于【工作 HTML 和需求材料】，
帮我设计【具体范围】的业务规则，并补充对应研发说明。
已有确认规则：【内容或来源】；需要你设计的部分：【具体问题】。
在授权范围内给出方案及理由；需要业务取舍的建议单独列为待确认，
已确认内容写入对应正文或页面说明，保持原型行为与文字一致。
同步更新【需求推进记录】中的规则位置、未决项和验证结果。
```

### D. 按已确认文字补充原型文档

```text
使用 $pm-prototype-workbench，把以下已确认内容写入【工作 HTML】。
全局描述：【文字或来源】。
上线后数据需求：【文字或来源】。
埋点说明：【文字或来源；不涉及则留空】。
产品共用规则和页面说明：【适用产品／页面／位置及文字】。
只更新指定内容，保留其他已编辑文字、说明和交互。
检查文字完整性、位置对应和保存恢复，交付原可编辑工作文件。
```

### E. 需要只读交接文件时

```text
请使用 $pm-prototype-workbench，将【当前工作 HTML】导出为只读 HTML，
保留已保存的需求正文、页面、交互和说明，并检查导出后可查看与定位。
保留可编辑原文件；将只读文件位置和对应修订日期记入【需求推进记录】。
```

只有用户手动使用导出入口，或实际提出这类导出要求时，才执行 E。导出前按 Skill 处理未保存说明和失效位置。

## 5. 记录、变更与日常维护

### 一份需求，一份推进记录

需求推进记录维护决定和进展；路径报告维护分析；原型／PRD 维护业务方案。用链接交接，避免为同一内容维护多个版本。用户修改过的内容先读取再继续，重要迭代保留可追溯备份。

每次交接核对三个问题：输入依据是否还是当前版本，未决事项是否影响接手工作，产出能否直接作为下一步输入。

### 状态分别记录

- **推进状态**：待分析、待决策、方案中、待评审、开发中、待验收、待发布、已发布／观察中、已复盘，或暂缓、取消。
- **交付证据**：分析、原型、代码、构建、测试环境、测试分发和生产环境分别记录，按项目实际存在的阶段填写。
- **效果结论**：尚未观察、证据不足、达到目标、部分达到、未达到；附适用窗口、数据来源和依据。

每个阶段的“完成”指该阶段已有相应证据。AI 生成草稿、内部走查、团队评审、用户验证、测试通过、生产发布和效果达成都按实际发生的状态记录。

### 变更怎么处理

发现新信息 → 说明与原决定的差异 → 判断是否影响目标、范围、规则、成本、排期、数据或验收 → 由相应负责人作决定 → 更新受影响文件 → 回归受影响部分。

已经确定的目标、非目标和关键决定不静默改写。事实更正保留来源；方案变化保留决定依据。日常不影响取舍的整理和既定范围内执行直接推进。

### 日常怎么维护

- 开始工作时看顶部摘要和统一待办，先处理当前阶段的阻塞。
- 完成一段工作后更新产出位置、阶段状态和下一步，实际发生变更时再写变更记录。
- 按团队已有节奏复查需求池与优先级；达到约定条件再做效果复盘，不为 SOP 额外设定固定会议或通知。
- 暂缓事项写清恢复条件；关闭需求前检查遗留任务是否已处理或明确转交。

## 6. 维护依据

本 SOP 由 `pm-product-sop` Skill 执行阶段判断、工具调度和需求记录维护。已有 `pm-master` 时，可将完整产品需求转交给它；两个专项 Skill 继续负责各自的分析与原型产物。

两个 Skill 的具体交付与验证要求以当前文件为准：

- [产品付费与权益路径分析 Skill](https://github.com/jiangxiaolin1995/pm-payment-journey/blob/main/SKILL.md)，以及[完整 HTML 与流程图交付规范](https://github.com/jiangxiaolin1995/pm-payment-journey/blob/main/references/html-flow-contract.md)。
- [交互原型工作台 Skill](https://github.com/jiangxiaolin1995/pm-prototype-workbench/blob/main/SKILL.md)，以及[PRD 纯文字需求说明约定](https://github.com/jiangxiaolin1995/pm-prototype-workbench/blob/main/references/prd-template.md)。

方案风险检查参考 [SVPG 的四类产品风险](https://www.svpg.com/four-big-risks/)；分析、交付与反馈持续衔接参考 [Atlassian 的产品发现说明](https://www.atlassian.com/agile/product-management/discovery)。具体操作流程按你的工作方式组织，执行中可根据真实需求试跑结果继续调整本文件。
